The harness

The harness is what stands between your agent and your live R or Python session: a few commands the agent calls, a skill that teaches it how, and rules that Corral enforces around every call, in its own code, whatever the model was told. This page is the map; each part links to its details.

The life of a request

  1. The agent asks. To look, corral vars --json and corral context --json, which run nothing. To run code, corral eval.
  2. Corral works out the rules for that session: your global profile, the project's, and the session's own mark, the stricter winning. It reads the folder the session is in from the process itself, so a setwd() counts at once.
  3. You approve it, if the rules say so. With ask, a popup shows the exact code, which agent asks and what it will see back: Enter runs it, n refuses it, and with no answer in 5 minutes nothing runs. With off, nothing runs at all.
  4. It runs where you see it. The code is typed into the console you are looking at, after a # corral eval line, one request at a time; several agents queue.
  5. The agent gets what the rules allow: everything printed, your review of it first, or only whether it worked and the shape of the objects. If the code moved the session into a stricter project, that request's result already comes back as the stricter project allows (its approval was asked under the old rules).
  6. It is recorded in the audit log on your machine: when, which agent, the code, and whether it ran.

Who decides what

You do. Every control is in the palette (ctrl+b space, type agents), and an agent can't loosen any of them through Corral's own commands without your yes in a popup. An agent with an unrestricted shell can go around those commands; its own permissions are what stop it (details).

What the agent knows

corral context --json tells it, in one call, which consoles run, whether SQL works there, and the rules as they apply to each session, so it plans around them (related code in one request when each one asks, shapes instead of values with restricted output) instead of learning them by being refused. It can read the rules; it can't change them. The palette's "What your agent sees" shows you the same, in words (details).

What always holds

  • In plain sight. Nothing runs in a hidden process; characters that would hide part of the code are written out, in the console and in the popup.
  • One at a time. Requests to a console queue; several agents never interleave.
  • Bounded. The agent stops waiting after a time limit (the code keeps running in your console), and the output is clipped before it reaches the agent.
  • Recorded. Every request, and every loosening of the rules an agent asked you for, in the local audit log: corral audit.
  • Any agent. Claude Code, Codex, Gemini CLI, opencode or another: the harness is shell commands and a skill in the open Agent Skills format.

What it doesn't do

  • It is not a sandbox. Approved code can do whatever your user can: read any file, use the network. An agent with an unrestricted shell can also act outside the harness; its own permissions close that gap.
  • What the agent reads goes to its model provider. Restricted output keeps values out of replies; for data that must not leave your organization, choose where the model runs.
  • Profiles follow folders, not files. A project's profile applies to sessions working in that folder; code reading its files by absolute path from elsewhere isn't covered.

The Security model explains each of these and has a setup for sensitive data. The Threat model sets them against the threats, one by one.
