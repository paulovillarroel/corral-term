Overview

Corral is a data science IDE for R, Python and SQL. R and Python are both first-class, with R first, and SQL runs in either one on DuckDB. It lives in your terminal. It gives you what you would otherwise open a desktop IDE for (a script you run piece by piece, a live console, your variables, tables and plots) next to your AI agents, and it opens in about 400 milliseconds.

Why it exists, where the name comes from and where it fits in your work: Why Corral.

What you get

  • A script editor (Fresh) where Ctrl+R runs the line or the selection and F5 runs the file, with completion from your live R session and formatting with Air.
  • A console for R, running on Ark, Positron's R kernel, or plain R if you prefer. Python runs in IPython inside your project's uv environment, in the same spot, one key away.
  • A variables pane that updates after every command, and a table viewer for View() that pages through millions of rows with DuckDB.
  • SQL in your session. In a .sql file, Ctrl+R runs a query on DuckDB in the console: your data frames are its tables, and the result is a data frame (SQL).
  • Plots in Mirador, a light page in your browser that shows each new plot about 80 ms after it is drawn.
  • Agents in the same session. Your agent (Claude Code, Codex, Gemini CLI or opencode) runs code in your console with corral eval, so its objects land where you can see them. By default, each request waits for your approval.
  • Objects that outlive a crash. If R or Python crashes, the next console gets your tables, models and functions back by itself (below).

Approval, audit and recovery

An agent working on real data runs under rules you set. They live in Corral's code, not in the agent's instructions, so they apply whatever the model decides:

  • Approval before it runs. With agents ask, the default, every request opens a popup with the exact code, which agent asked and what it will see back. Enter runs it and n refuses it; with no answer in 5 minutes, nothing runs. Loosening these settings from an agent's pane needs your yes too.
  • What the agent reads. Full results, your review of each one first (agent_output review), or only whether the code worked and the shape of the objects, without their values (agent_output structure).
  • Sensitive sessions. corral_sensitive(), in R or Python, makes one session stricter than the rest: every request needs your approval, and results never go back in full. It lasts until that console ends, and a session brought back after a crash stays sensitive.
  • An audit log. Every request is recorded on your machine, readable only by you: when, which agent, the code, and whether it ran, was refused or went unanswered. corral audit shows it; entries are kept 90 days by default.
  • Recovery after a crash. Corral keeps a checkpoint of each console's objects. If R or Python crashes, or herdr or WSL closes, the next console in the project gets back the tables, the models, the functions you wrote and the packages you loaded, about 1.2 seconds after R crashes. Keeping the checkpoint costs the prompt a few milliseconds (Consoles).

Corral is not a sandbox: approved code runs with your permissions, and what the agent reads goes to its model provider. The Security model says what each control covers and what it doesn't, and has a checklist for sensitive data such as health records.

R and Python, both first-class

Both languages get the whole workbench: the editor with completion and formatting (Air for R, Ruff for Python), the console, the variables pane, View(), plots in Mirador and agents running code in your session. R comes first: it is the default console, and its language server is Ark's, which knows your live objects.

Projects often mix the two, so there is no language to choose up front. Running a .py file (or ctrl+b y) brings the Python console into the console spot; the one you are not using waits in a hidden tab and keeps its state.

SQL runs in either one, on DuckDB: in a .sql file, Ctrl+R runs a query in the console in view, your data frames are its tables, and the result is a data frame in the session (SQL).

How it is built

Corral is one small program, corral, written in Rust with no dependencies. It talks to the pieces that do the heavy lifting, most of them written in Rust as well:

PieceWhat it does here
herdr TUIThe terminal workspace: herdr's terminal version, not the Herdr App. Every console lives in a herdr pane, so closing the window loses nothing.
ArkThe R kernel from Positron: the console and the language server, which knows your live objects.
FreshThe script editor, with a Corral plugin for running code and keeping the draft.
MiradorCorral's own viewer in the browser, written from scratch and exclusive to Corral: a Rust server inside the corral binary, with DuckDB behind its tables. Your plots, and tables when you send them there.
DuckDBQueries the tables you open with View(), one page at a time, and runs SQL in your session.
uv, ty, RuffPython: the console's environment, completion and diagnostics.

The only parts that are not Rust run inside your own sessions: a small R file that R loads, a Python module that IPython loads, and the editor plugin. Architecture has the diagrams: the layers, what runs where, and how code, tables and plots travel.

When Corral acts

Corral stays out of the way of everything you already have:

  • In R, it only switches on in the console a Corral layout opens, or in an R where you turn it on (ctrl+b m, or corral_activate()). Any other R works as always, with its own View() and graphics device.
  • The layout (script, console and variables) only appears when you ask for it: corral, ctrl+b a or ctrl+b shift+s.
  • Agents use your console only when the workspace has an active Corral console; otherwise they work as usual.
