Why Corral

Corral starts from one idea: in data science the work happens in a live session, so an agent that helps you should work there too, where you can see it. This page explains that idea, where the name comes from, and where Corral fits in your work.

The name

Corral runs on herdr, and a herd needs a corral. herdr keeps the herd: workspaces, tabs and panes, and the agents and programs running in them. Corral is the fenced place where you gather that herd to work: the consoles, the editor, the variables, the tables, the plots and the agents, together and under rules you set.

The word works a second way too. A corral is a bounded space where things meet and work gets done. It isn't there to lock anything in; it gives your tools and your agent one place to work together, with clear rules.

The session is the unit of work

Coding agents grew up in software engineering: they edit files, run tests and hand you a diff. Analysis works differently. It is exploratory and it has state: the work in progress is the objects in memory, the data you loaded, the model you fitted a minute ago. Copying code from a chat into a console, or running an agent's script again to get its objects back, breaks that flow.

In Corral the agent runs its code in your console, with corral eval. What it creates lands in your session next to what you created, and you can look at it, change it or plot it at once. It is the old habit of R and S, working at the prompt, carried over to working with agents.

A harness, not an AI

Corral has no chat and no model of its own. The agent is the one you already use (Claude Code, Codex, Gemini CLI, opencode…), in its own pane. Corral provides what sits between it and your session: a few shell commands, a skill in the open Agent Skills format that teaches the agent to use them, and rules that live in Corral's code, so they hold whatever the model was told. Any agent that can run a shell command can work with it.

You see it, and you approve it

The code an agent runs is typed into your console, one request at a time, and written to a local audit log. Seeing code go by is not the same as reading it, so by default every request waits in a popup until you approve it (agents ask). If you prefer speed, corral config agents on lets the agent run without asking, still in plain sight. The Security model has the details.

The roles stay clear. You control the code, the data, the sessions and the analytic decisions; the agent explores, runs, transforms, models and proposes. The conclusions are still yours.

Light, for a day's work

If your work already happens in the terminal with an agent, a desktop IDE of several gigabytes next to it is mostly weight. Corral is one Rust binary with no dependencies, its own processes use a few megabytes each, and a layout has R ready in under half a second. Those figures are measured, and the Performance page shows how and what they leave out.

An IDE is for working all day, not for opening and closing, so what counts most is that Corral behaves the same in the evening as in the morning: View() as fast the twentieth time as the first, R's memory steady, and temporary files that don't pile up.

Processes and files, not libraries

Corral leans on engines that already do their job well (herdr, Ark, Fresh, DuckDB, uv) and talks to them through processes and plain formats: herdr's socket, the Jupyter protocol, Parquet and JSON files. SQL is the exception: DuckDB loads inside your R or Python session at the first query. The table viewer and Mirador run outside your session, so if one of them fails, your session doesn't. The same care goes for your machine: the installer never uses sudo, keeps a copy of each file it changes, and corral uninstall takes Corral out, leaving your settings and sessions.

Where Corral fits

An analysis usually goes through five stages:

  1. Preparation. Import the data, set up the environment, look at its structure.
  2. Exploration. Variables, distributions, anomalies, relationships, missing data.
  3. Assisted iteration. Ask the agent for calculations, transformations, analyses or tests on the session.
  4. Validation. Inspect the results, read the code, check the assumptions.
  5. Formalization. Turn what worked into reproducible scripts, tests and pipelines.

Corral is made for the first four, and above all for exploration and iteration, where the live session matters most. Formalization belongs to your project: the scripts you save, your repository, your tests and your pipelines. A live session is quick to work in and easy to lose, so the draft is temporary on purpose: save the code that matters (Ctrl+S, or ask the agent to save the draft), and the audit log keeps what agents ran.

Checking what is already built

A good part of data science is not building something new but keeping an eye on systems, models and algorithms already in use: how a model performs on this month's data, whether it treats some group worse, whether its inputs drifted, whether an algorithm still does what it should. That is analysis, not development, and it doesn't need the whole infrastructure up. Load the data and the model, ask your questions, look at the answers: a tool that opens in under a second and stays light is enough.

What Corral leaves to other tools

  • Your team's development workflow. Reproducibility, version control, tests, dependency management and code review belong to your workflow, not to the IDE.
  • Positron, RStudio and VS Code. They are still the right tools for heavier work, and Corral doesn't touch them.
  • A sandbox. Code an agent runs has your user's permissions. The Security model says what Corral enforces and what it doesn't.
