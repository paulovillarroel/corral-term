Security profiles

Three names for the harness's settings, so you set them in one step, for all your work or for one project folder. The stricter one wins: a project can make things stricter than your global profile, never looser.

ProfileAgentsWhat they get backFor
openrun code without askingeverything printedpublic or synthetic data
standardask before each requesteverything printedthe default
sensitiveask before each requestonly the structure; every session is sensitivepersonal or clinical data

Set one

$ corral profile sensitive
$ corral profile sensitive --project
$ corral profile sensitive --project /data/clinical-study
$ corral profile --project --clear

Without --project, the profile is for all your work: it sets agents and agent_output. With --project, it is for one project folder (the folder you give, else the one the console in view started in) and every session that starts or runs in it or below it, without anyone remembering to call corral_sensitive(). --clear removes a project's own, and the global one applies there again.

In the palette (ctrl+b space): "Agents: open profile", "standard profile", "sensitive profile", "this project is sensitive" and "this project follows the global profile".

See which one applies

$ corral profile
$ corral profile --json

corral profile shows the global profile, this project's, and the rules that result here; --json gives the same to scripts (global, project with its folder and profile, the resulting profile, access, output and sensitive, and every project with a profile). The variables pane's header names the profile in effect, profile: open say, in the accent colour when it is sensitive, and corral context gives it to the agent.

The stricter wins

Corral works out each request's rules from your global profile, the project's and the session's own mark (corral_sensitive()), and takes the strictest of each part: who approves (off before ask before on) and what comes back (structure before review before full). Nested projects with different profiles get the strictest of them. A session that started in a sensitive project stays sensitive if it moves to another folder. Working this out takes about 2 µs per request.

Making things stricter never asks. A looser profile, or removing a project's, from an agent's pane waits for your approval in a popup, as corral config does.

What a project's profile follows

Sessions, by the folder they work in: the one they started in, and the one they are in now, which Corral reads from the process itself (/proc/PID/cwd), so a setwd() or os.chdir() counts at once. A request that moves into a sensitive project gets that project's output for its own result, with a note saying so, and the next request already asks; approval can't be asked after the fact, so what that one request ran, it ran.

It doesn't follow files: code that reads a project's files by absolute path from a session in another folder isn't covered, and approved code can do anything your user can (read any file, use the network). For data no agent may reach, make sensitive your global profile on that machine, and deny the agent's own tools those folders (for sensitive data).

Where it is kept, and teams

A project's profile lives in Corral's settings (projects in ~/.config/corral/config.json), not in the repository. That is by design: a repository you clone can't loosen your rules. It also means each person sets it in their own Corral, so in a team, make corral profile sensitive --project part of setting up a machine for that project.
