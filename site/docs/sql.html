SQL

SQL runs in your live session, on DuckDB, in the R or Python console you already have open. There is no database to set up and no second console: your data frames are tables under their own names, and every result comes back as a data frame you keep working with, in R or Python.

Run it

-- name: by_region
SELECT region, count(*) AS orders, sum(amount) AS total
FROM sales
GROUP BY region
ORDER BY total DESC;
  • In a .sql file, Ctrl+R runs the statement under the cursor, up to its ; and with the comments above it, and moves to the next one. F5 runs the whole file.
  • Anywhere else, in an R script, a Markdown file or the terminal, select the SQL and choose Console: run the selection as SQL in the palette (ctrl+b space).
  • In the console it is a function, the same in R and Python: corral_sql("SELECT …"), with name = to name the result.
  • From a terminal or a script: corral send --lang sql 'SELECT …'.

It runs in the console in view: R by default, Python after ctrl+b y. The query and its result show in the console like any other command.

Your data frames are tables

A name in the query that is a data frame of your session is a table: a data.frame or tibble in R, a pandas, polars or pyarrow table in Python. DuckDB reads it where it is, without a copy: a million rows take about 2 ms to make visible. A DuckDB table of the same name, one you made with CREATE TABLE, keeps the name.

SELECT s.region, t.target, sum(s.amount) AS sold
FROM sales s JOIN targets t USING (region)
GROUP BY ALL;

Files and databases

  • Files are tables too: FROM 'data/sales.parquet', FROM 'data/*.parquet', FROM read_csv('sales.csv'), FROM 'events.json'.
  • Tables and views you make with CREATE TABLE or CREATE VIEW last as long as the session; they don't come back after a crash (DuckDB's database is in memory), while results kept as data frames do.
  • ATTACH 'project.duckdb' AS project works on a DuckDB database file. DuckDB's extensions attach PostgreSQL, MySQL and SQLite databases the same way; DuckDB downloads an extension the first time it is used.

The result

  • The last query's result goes into sql_result, or into the name a -- name: x line gives it, so it shows in the variables pane and opens with View().
  • Several statements run in order, and each -- name: keeps its own result.
  • The console shows the first 10 rows and a line with the row count, the time and the name: # 3 rows · 21 ms → by_region.
  • In Python the result is a pandas DataFrame, or polars when that is what the session uses, or else a pyarrow Table.
  • A mistake shows DuckDB's own message, with the line and the place it points to.

Agents

Agents run SQL with corral eval --lang sql, through the same harness as R and Python: it asks before running unless you set agents on, the audit log records it, and the limits you set on what agents see apply. Corral's skill tells them to prefer it for joins and aggregations over big tables.

$ corral eval --lang sql 'SELECT region, count(*) FROM sales GROUP BY 1'

Speed

DuckDB loads with the first query of a session, about 0.2 seconds in R and 0.1 in Python, so a session that never runs SQL doesn't pay for it and the console starts as fast as ever. After that the time is the query's own: a GROUP BY over a million rows takes about 20 ms, the same as DuckDB on its own. Performance has the measurements.

Two DuckDBs

Corral uses DuckDB in two places, and they don't have to be the same version:

WhereWhich DuckDBWho picks the version
The table viewer and Mirador (View())The DuckDB command line, a program of its own that the viewer startsCorral: the installer brings 1.5.6 and checks its SHA-256. DuckDB 2.0.1 starts three times slower (22 ms against 8 ms), so the viewer stays on 1.x for now.
SQL in RThe duckdb package, inside your R sessionYour R library: whatever version is installed there; the installer adds the one Posit's package manager had three days earlier, already compiled
SQL in PythonThe duckdb package, inside your Python sessionuv: the latest, or the version your project pins

They never share a database file. View() hands the viewer a Parquet file (CSV as a last resort), which every DuckDB version reads the same way; SQL results live in your session as data frames. The one place they share is ~/.duckdb, where downloaded extensions go, and DuckDB keeps a folder per version there.

If you create a DuckDB database file from R or Python (ATTACH 'project.duckdb') and open it by hand with the duckdb command, an older command line may not read a file a newer package wrote. Corral itself never opens such a file with the command line.

What it needs

In R, the duckdb and DBI packages: the installer puts them in your R library, already compiled, on Ubuntu 20.04 to 24.04 and Debian 11 and 12; elsewhere duckdb has to compile for a while, so the installer shows the command instead. The Python console brings duckdb with it. R's duckdb keeps its extensions in ~/.duckdb when that folder exists, shared with the DuckDB command line, and in a temporary folder for the session otherwise.
