Install

Before you start you need a Linux system (or Windows with WSL) and R. The installer brings everything else, and it checks all of it before it changes anything. If herdr or the R package jsonlite is missing, or herdr is too old, it offers to install or update them; if something else is missing, it tells you what to run and stops.

On Windows: set up WSL first

Corral runs on Linux. On Windows it runs inside WSL (Windows Subsystem for Linux), which gives you a real Ubuntu next to Windows, with no virtual machine to manage. You set it up once, in about ten minutes, and you don't need to know Linux for it: copy each command, paste it, and press Enter. On Linux, skip to Before you install.

  1. Check your Windows. You need Windows 11, or Windows 10 version 2004 or later. To see yours, press Win+R, type winver and press Enter.

  2. Install WSL with Ubuntu. In the Start menu, type PowerShell, right-click it and choose Run as administrator. Paste this and press Enter:

    PS> wsl --install

    It turns on WSL 2 and installs Ubuntu. Restart the computer when it finishes.

  3. Create your Linux user. After the restart, open Ubuntu from the Start menu. The first time, it asks for a username and a password for Linux; they don't have to match your Windows ones. While you type the password, nothing appears on the screen: that's normal, keep typing and press Enter. Keep it: Ubuntu asks for it when a command starts with sudo.

  4. Bring Ubuntu up to date. In the Ubuntu window:

    $ sudo apt update && sudo apt upgrade -y

  5. Install R with rig. rig installs R in your home folder and sets up ready-built packages, so nothing has to be compiled:

    $ curl -LsSf https://r-lib.github.io/rig/install.sh | sh
$ rig add release

    Close Ubuntu and open it again, so it finds R.

  6. Install Corral with the line in Install with one line. It checks everything first. It offers to install herdr, the terminal workspace Corral lives in, and the R packages it needs: press Enter to say yes. If anything else is missing, it tells you, with the command to fix it.

Working in WSL

  • Where to open it. Ubuntu is in the Start menu. Windows Terminal (it comes with Windows 11; on Windows 10, get it from the Microsoft Store) opens it in a tab: choose Ubuntu from the menu next to the tabs. Then type herdr and press Enter.
  • Keep your projects in Ubuntu. Work in your Linux home folder, ~ (for example ~/projects/sales), not under /mnt/c/…, where your Windows C: drive shows up: Microsoft recommends it because it's much faster. explorer.exe . opens the folder you're in in Windows' File Explorer, and \\wsl$ in its address bar shows all of Ubuntu's files.
  • Your Windows browser does the rest. Mirador and R's help pages open in it.

Before you install

You don't need to check these by hand: the installer does. It offers to install herdr and the R package jsonlite when they are missing, or to update herdr when it is older than Corral needs, and shows the command for anything else.

What the installer brings

You don't install these yourself. The installer puts corral in place and downloads the rest if you don't have them: the programs inside ~/.local, the packages in your R library and uv's cache:

ProgramWhat it does in Corral
FreshThe script editor.
DuckDBQueries the tables you open with View().
AirFormats R code.
ArkThe R console, Positron's R kernel. The installer brings version 0.1.252, the one Corral was tested with.
The R package httpgdDraws R's plots, for Mirador and for the agent. It goes in your own R library, without sudo. If it can't be installed (on Linux it needs cairo and libpng from the system), Corral installs and works anyway, without R's plots in Mirador, and the installer says how to add it.
The R package nanoparquetSaves the tables View() opens: big tables open faster, and R's memory stays steady in a long session. It goes in your own R library, without sudo, already compiled on the Ubuntu and Debian releases Posit's package manager builds for and on a Mac with R from CRAN or rig, from source otherwise.
The R packages duckdb and DBISQL in R runs on them (SQL). They go in your own R library, without sudo, already compiled on Ubuntu and Debian and on a Mac with R from CRAN or rig; elsewhere duckdb has to compile, which takes a while, so the checklist shows it as optional.
The Python console's packagesWith uv, it puts IPython, cloudpickle, pyarrow and duckdb in uv's cache, so the first Python console starts at once. duckdb runs SQL, imported only with the first query. pyarrow lets View() save pandas tables as parquet, about six times faster than CSV and with their types.

If your R has pak, the installer installs R packages with it, as you would; otherwise with install.packages(). They come from Posit's package manager as it was three days ago, so no package is newer than 72 hours and everyone installing that day gets the same versions, already compiled where Posit builds them. If R already has a repository that isn't a public one, such as an institution's mirror set in R's Rprofile.site, the installer uses that one instead; in a network that blocks CRAN and Posit, it's the one that works. CORRAL_R_REPOS picks the repositories yourself (URLs separated by spaces or commas). pak never installs system libraries here, since that takes sudo: if a package arrives but doesn't load, the installer shows the apt-get line pak gives for what it needs, for you to run.

On a Mac with R from CRAN or rig, packages come compiled from the same snapshot, except unigd and httpgd, which draw R's plots: the snapshot has httpgd only as source there, and its build of unigd needs XQuartz, which a Mac doesn't have, so those two come compiled from CRAN, in the versions the snapshot has, and what they need from the snapshot. With Homebrew's R, packages compile from source. On any system, what R says while the installer puts packages in goes to ~/.local/state/corral/install-r.log, with the reason when a package went in but doesn't load.

A program you already have on your PATH is left as it is, and Corral uses yours. Every download is checked against a SHA-256 before it is used: Corral's own package against the one published with it, and Fresh, DuckDB, Air, Ark, herdr and uv against the ones written in Corral's code. If Ark can't be downloaded, the R console is plain R until corral ark --install gets it.

Install with one line

$ curl -LsSf https://corral-term.dev/install.sh | sh

The installer speaks English. To read it in Spanish, set CORRAL_LANG=es; an update already speaks the language you chose with corral config language.

$ curl -LsSf https://corral-term.dev/install.sh | CORRAL_LANG=es sh

First it prints a checklist of everything above: what you have (✓), what is missing (✗), what it will download (↓) and what is optional (!). Under each missing item it shows the command that fixes it. If anything required is missing, it changes nothing and stops: fix those and run the same line again. This is what it looks like when everything is there:

  ✓ R                 4.6.1
  ✓ R packages        jsonlite

If you have several agents and haven't chosen one, it asks which one the agent pane opens; Enter leaves it to Corral, which opens the first one installed. It asks once, and only in a terminal where you can answer; later, the palette changes it ("Agent: … in its pane").

How the download is checked

  • It installs a published version, the latest unless you pick one with CORRAL_VERSION=v0.1.3, and says which. It never falls back to unreleased code: if the download fails, it stops and says why.
  • Before opening the package it checks its SHA-256 against the one published with that version, and stops if they differ. That catches a download that arrived broken or changed on the way. Both files come from the same release, though, so someone able to publish there could replace both.
  • The attestation covers that case. Each package carries a build provenance attestation, signed by GitHub when the project's workflow builds it, which proves the package came from that workflow and that version's code. If you have the GitHub CLI (gh 2.49 or later, logged in), the installer checks it and stops if it doesn't hold; without it, it says the attestation wasn't checked. You can also check it yourself, with the package for your system (from the first macOS version, corral-term-aarch64-macos.tar.gz or corral-term-x86_64-macos.tar.gz on a Mac): 
    $ gh attestation verify corral-term-x86_64-linux.tar.gz --repo paulovillarroel/corral-term
  • Fresh, DuckDB, Air and Ark, which it downloads when you don't have them, and herdr and uv, when you say yes to them, are each checked against a SHA-256 written into Corral's own code for the version it installs, so the check doesn't depend on their projects publishing one. A version of Ark you choose yourself (corral ark --install 0.1.250) is checked against the SHA-256 GitHub reports for it, and refused if there is none.
  • The script runs from a single function called on its last line, so a download cut halfway runs nothing.

It never uses sudo and only writes inside your home folder. It also checks that ~/.local/bin is on your PATH, since R and the editor look for corral there. If it isn't, it offers to add the line to ~/.bashrc (or ~/.zshrc), after saving a copy of the file; uninstalling leaves that line, since herdr and other tools live there too. Without a terminal to ask in, add this line at the end of ~/.bashrc (or ~/.zshrc) and open a new terminal:

export PATH="$HOME/.local/bin:$PATH"

When it finishes, go to a project folder and type corral: herdr opens with the workspace. The quick start takes it from there.

What changes on your machine

Before it touches a file of yours, the installer saves a copy next to it, named *.before-corral-DATE.

  • Corral goes in ~/.local/share/corral-term, and the command in ~/.local/bin/corral. To use another folder, set CORRAL_DIR=/other/folder before you install.
  • herdr: it links Corral's plugin and adds its shortcuts at the end of ~/.config/herdr/config.toml, between two Corral comments. If you already use one of those keys, it leaves yours and tells you; corral keys --change gives the Corral action another key (see Keyboard shortcuts).
  • R: one line in ~/.Rprofile that loads Corral. It only switches on in the consoles Corral opens; your other R sessions don't change.
  • Fresh: it adds Corral's shortcuts and language servers to ~/.config/fresh/config.json without removing your settings, and links its plugin.
  • Agents: it links Corral's skill in ~/.agents/skills/corral, the shared folder of the open Agent Skills standard, which Codex and other agents read, in ~/.claude/skills/corral if you have Claude Code, and in ~/.gemini/skills/corral if you have Gemini CLI. If you already have a folder of your own with that name, it leaves it alone.

The line in ~/.Rprofile looks like this, with the full path to your copy of Corral:

if (interactive()) try(source("~/.local/share/corral-term/r/corral.R"))  # Corral

Anonymous install count

When an installation finishes or stops, and when Corral is uninstalled, the installer sends one anonymous ping to corral-term.dev, so the project knows how many people install Corral, from which countries, on what, and what keeps people out. The ping says only:

  • the version of Corral (0.2.2);
  • the system: Linux, WSL or macOS (or another system, when the installer stops because Corral doesn't run there);
  • whether it is a new install, an update, a stop or an uninstall; on an update, the version it replaced (0.1.29);
  • on a stop, which requirements were missing, by the names Corral gives them: herdr, herdr_old, r, r_packages, folder, or system, arch and basics when the installer stops before Corral is on the machine;
  • when the download doesn't check out, which check failed: sha256 (it doesn't match the published SHA-256), sha256_missing (that version has none published) or attestation (the build provenance attestation didn't verify). That ping is an alarm: it tells the project a published package may be broken or replaced;
  • when corral install installs, updates or stops, where Corral runs, in coarse categories: the agent the layout opens (claude, codex, gemini, opencode, other for any other command, or none), the Ubuntu or Debian release by its codename (noble, bookworm; other for anything else, macOS included), herdr's version (0.9.5, or none), R's major version (4.6, or none) and whether uv is there for the Python console;
  • when an install or update finishes, which of the R packages the installer puts in by itself didn't go in, if any: httpgd, nanoparquet or duckdb, so the project sees where installs get stuck;
  • whether it came from the published package or a clone.

The country comes from the request itself, through Vercel's geolocation; the IP address is never stored. No names, paths, hostnames, no identifier of the machine, nothing about your data or code. The site checks each field against a fixed list or pattern and turns away a ping with anything else, so nothing else gets stored, and it limits how many pings one address can send in a few minutes. The code that receives it is api/installed.js. Checking (--check) sends nothing.

To install without it, set CORRAL_NO_TELEMETRY=1 (DO_NOT_TRACK=1 works too):

$ curl -LsSf https://corral-term.dev/install.sh | CORRAL_NO_TELEMETRY=1 sh

Once Corral is installed, corral config telemetry off (in the palette, Install count: don't count my installs) turns it off for good, in every shell. The environment variable only holds where it is set, and an agent's shell doesn't read your .bashrc.

New versions

When you open the workspace, Corral asks GitHub which version is the latest, at most once a day and in the background, so the layout never waits. When there is a newer one, the foot of the variables pane says so, in the accent colour, until you install it ("Corral 0.2.3 is out: ctrl+b space → Update"), and the palette's entry names it ("Update: Corral 0.2.3 is out, install it"). corral update installs it, and so does that entry. If you turned on herdr's toasts ([ui.toast] delivery = "herdr" in herdr's config.toml; they are off by default), a toast says so once too. The request is the one the installer makes too (GitHub's link to the latest release) and carries nothing about you.

corral config update_check off (in the palette, Update: don't check for new versions) stops it, and so does the sensitive profile; corral update still checks when you run it, and corral update --check (in the palette, "Update: look for a newer version, without installing") only looks, in a popup. Without the daily check, a month without a look doesn't go unnoticed: after 30 days, the foot of the variables pane says so ("No update check in 30 days: ctrl+b space → Update") and the palette's entry says how long it has been. It counts from the last look that reached GitHub, the daily one or yours (an attempt without a connection doesn't count), or from the installation, from files on your disk; looking puts it away for another 30 days.

Check without installing

To see the checklist without changing anything, add --check:

$ curl -LsSf https://corral-term.dev/install.sh | sh -s -- --check

Once Corral is installed, corral install --check does the same.

Install from a clone

From a copy of the repository, the installer uses that copy where it is, without downloading Corral. It's the way to work on Corral itself, or to try something that isn't published yet.

$ git clone https://github.com/paulovillarroel/corral-term.git
$ sh corral-term/install.sh

If the copy has no compiled corral, the installer builds it with cargo. When you change something in rs/, build it again with cargo build --release; corral --version tells you which folder the binary you are using comes from.

Tests

$ cargo test --manifest-path rs/Cargo.toml
$ cargo test --release --manifest-path rs/Cargo.toml --test live -- --ignored --test-threads 1

The first runs the unit tests (the JSON, TOML and zip readers, the ZMTP and Jupyter protocol Corral speaks to Ark, the audit log's dates) and checks Mirador's API: without its token, or from another address, it answers 403. GitHub runs them on every pull request.

The second runs the live tests. Each starts its own herdr server with an R console, and Python when the test needs it, and checks what agents rely on, in both languages: two agents asking at once take turns, a timeout leaves the code running and keeps its output, Ctrl+C stops it and keeps the session, a crash is reported at once and the next request gets a new session, and the variables are never read half-written. For R they also check that a crashed R comes back by itself and that the editor's language server reaches Ark; for both, that the objects come back after a crash, and that closing on purpose starts clean. checkpoints_cost_report, python_checkpoints_cost_report and restore_time_report print the measurements in Performance. They need herdr, R, Ark and uv, and leave your herdr, sessions and settings alone; their panes run /bin/sh, so they use the corral being tested even when your .bashrc puts another one first.

Update

$ corral update

It finds the latest published version and, if it is newer than yours, runs the same install line as the first time, which you can also run yourself. That replaces your copy of Corral and doesn't repeat what is already done: in herdr's configuration, for example, it only adds shortcuts that are new. corral update --check only says whether there is a newer version, and the palette has "Update: install the latest version of Corral". Consoles already open keep the version they started with; the next ones you open use the new one.

If you installed Corral from a copy of the repository, update that copy: git pull in it, then sh install.sh, which builds the new version.

corral install checks and repairs the installation from the copy you have, without downloading Corral again, and corral install --check only checks.

Uninstall

$ corral uninstall

corral uninstall removes the herdr plugin and shortcuts, the line in ~/.Rprofile, Corral's shortcuts, theme and language servers in the editor (and gives you back your own shortcuts it had replaced), the skill, the programs it downloaded (Fresh, DuckDB, Air and Ark) and its copy of Corral. herdr and uv stay, as do the R packages and uv's cache. It saves a copy of each file it changes, and it never deletes a cloned copy of the repository.

Your settings and sessions stay in ~/.config/corral and ~/.local/state/corral (under $XDG_CONFIG_HOME and $XDG_STATE_HOME if you set them), in case you come back. The second holds the checkpoints (copies of your objects), the audit log, the consoles' history and the script drafts: if you won't come back, delete both folders whole.

Publish a version

The installer downloads the package of the latest version published on GitHub. That package includes corral already compiled, so nobody needs Rust. The action .github/workflows/version.yml builds it when you push a tag that starts with v, and publishes it with its SHA-256 and a build provenance attestation. First put the new number in rs/Cargo.toml and herdr/herdr-plugin.toml, so corral --version, the herdr plugin and Mirador say the same, and write its section in CHANGELOG.md (## 0.2.3): it becomes the release notes, and without it nothing is published. The README, the landing page's version link, the sample output on this page and the header of every docs page name the version too, and rs/tests/version.rs fails until they all say the new one. rs/Cargo.lock must match too, and that test doesn't read it: cargo build --manifest-path rs/Cargo.toml from the repository's root updates it, and it has to be committed, since the tests in GitHub and the release build use --locked and stop without it. Run the live tests too, which check Corral with a real herdr, R and Python: in GitHub, Actions → Live tests → Run workflow, or on your machine, from the repository's root, cargo test --release --manifest-path rs/Cargo.toml --test live -- --ignored --test-threads 1. Then tag it with that number:

$ git tag v0.2.3
$ git push origin v0.2.3

There is one package per system: Linux x86_64, with a static (musl) binary that runs on any x86_64 Linux, WSL included, and macOS on Apple silicon and on Intel, built on a Mac. The release goes out once all three are built, so no version is published without one of them. A pull request that changes the workflow runs it too, building every package without publishing anything.

The package appears on the release a few minutes after the tag, when the workflow finishes; until then the installer keeps installing the previous version. A version without its package or its SHA-256 doesn't install: the installer stops and says so, and never builds from main instead.

When Fresh, DuckDB, Air or Ark move to a new version, their SHA-256s change too, one per system: put them next to the version in rs/src/install.rs (rs/src/setup.rs for Ark). GitHub shows them on the release page, and this prints them:

$ gh api repos/posit-dev/air/releases/tags/0.13.0 --jq '.assets[] | .name + "  " + .digest'

macOS

The macOS version, for Apple silicon and Intel, is in development. Corral's code runs on a Mac and its tests pass there, and a Mac in the project's tests installs it from scratch with only R from CRAN, but no version with macOS packages is published yet. Until one is, the install line stops on a Mac and says so.
