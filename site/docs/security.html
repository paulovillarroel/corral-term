Security model

Corral runs everything on your machine. Working with an agent, though, means its model sees whatever the agent reads, and that model may be hosted by a provider outside your organization. This page says what goes where, what Corral enforces whatever the agent was told, what it doesn't, and how to set it up for sensitive data such as health records.

Running locally is not the same as staying inside your organization. Corral executes code on your machine, but the agent's model may be hosted elsewhere, and what the agent reads (results, plots, errors) is sent to it under that provider's terms.

Every connection Corral makes

These are all the connections Corral itself opens beyond your machine. None carries your data, your code or anything from your sessions. Like any download, each request shows your address to the server and names its program in a User-Agent; three say more about your system: the install count, R's package downloads (R's version and platform) and uv's (its version, Python's, your Linux distribution and kernel, and the processor, as pip's do). Most happen only when you install or update; while you work, Corral makes one at most: the daily question about new versions, or a download the Python console or its editor needs the first time.

Everything else stays on your machine: Mirador and httpgd listen only on 127.0.0.1, Ark talks to Corral over Unix sockets in a private folder, and the table viewer's DuckDB reads files on your disk. What isn't Corral's goes on as it would without it: code that runs in your console (yours, or an agent's you let through), packages you install, DuckDB extensions your SQL asks for (a URL in read_parquet), and the agent with its model provider.

herdr, the terminal Corral runs on, makes two connections of its own, in the background: whether there is a newer herdr (to herdr.dev, or formulae.brew.sh for a herdr installed with Homebrew), and updates to how it recognizes agents in panes (herdr.dev). Neither carries anything of yours. The sensitive profile turns both off for you (no connections of its own). To turn them off without it, set these two keys in the [update] table of herdr's config, adding the table if there is none (a second [update] would make herdr ignore the file); herdr then recognizes agents with the rules it came with. The config is ~/.config/herdr/config.toml, or herdr/config.toml under $XDG_CONFIG_HOME when it is set, or the file HERDR_CONFIG_PATH names:

[update]
version_check = false
manifest_check = false

Two tests keep this list whole. One reads the code: each place in Corral that can open a connection is marked with the row it belongs to, and the test fails when one isn't marked or listed here, or when a row here is no longer in the code. It finds those places by the calls that open connections (curl, uv, gh, sockets, the R and Python download functions), so a way it doesn't know of would pass it; the second test is there for that. The other watches Corral run: with strace following every process (herdr and what it starts, the R console, Ark, the variables pane, httpgd, Mirador, DuckDB) through a console, corral eval, a plot, the table viewer, SQL and the variables, it fails on any connection beyond 127.0.0.1 and local sockets, and on any DNS query, a resolver on the machine included. It first makes a connection on purpose and fails if it doesn't see it. In its last run it followed several hundred connections, all of them on the machine. A third checks that with the sensitive profile opening the workspace doesn't ask GitHub, though the daily check is on and due.

What Corral enforces

These controls live in Corral's code, not in the agent's instructions: they apply whatever the model decides.

Access levels

$ corral config agents ask
$ corral config agents on
$ corral config agents off
  • ask (the default): every request opens a popup with the exact code, which agent asked (Claude Code, Codex… and its pane, or "outside herdr" when no pane did) and what it will see back. What you read is what runs: control and invisible characters, which a terminal would act on or draw as nothing, show as ␛, ␍ or <U+202E> under a warning, and long lines wrap instead of being cut. The console prints such code written out too, before its echo. Enter runs it; n or Esc refuses, and the agent is told not to try again unless you ask. With no answer in 5 minutes, nothing runs. A missing or mistyped setting also asks. The popup ignores keys for its first 0.6 seconds, so a key you meant for another pane, an Enter sending a message to your agent for instance, can't answer it.
  • on: an agent's corral eval runs in your console, where you watch it, without asking first. Whatever can call corral eval as you, an agent or a script, can run any code in your session. Watching is not the same as reading, so choose it only when the speed is worth more than reading every request.
  • off: corral eval refuses everything, and corral vars --json lists nothing.

Restricted output

$ corral config agent_output structure

The code still runs on your real data and you see its output in your console, but the agent only gets back whether it worked, the first line of an error (up to 200 characters), how many warnings there were, how many lines it printed, and the shape of the session's objects (up to 40): names, classes, the dimensions of tables, the signatures of functions. No printed values, no previews, no plots. For example:

[corral] restricted output: the agent doesn't see values (5 lines printed in the user's console)
[corral] 1 warning(s), not shown
[corral] objects: patients (data.frame, 3 × 3); overview (summaryDefault)
[corral] 1 new plot(s) for the user (ctrl+b f); not shared with the agent (restricted output)

full (the default) returns everything.

Review mode

$ corral config agent_output review

The middle ground, for when the agent should help you draw conclusions but you want to see what it reads first. The code runs; then a popup shows you the result exactly as the agent would get it, with any new plots, without its colors and with any other character that could hide text written out. Enter shares it. n keeps it to you, and the agent gets only the structure, plus a note to ask you what you found. You might share a table of counts and keep a listing of patients, for example.

Code that prints nothing, gives no warning and draws no plot, like an assignment, doesn't ask: there is nothing to see, and the agent gets the result as it is. With no answer in 5 minutes, the result is kept. corral vars --json leaves out previews of values in this mode, since they would skip your review.

Profiles

Three names for these settings, open, standard and sensitive, set in one step for all your work or for one project folder, the stricter winning: corral profile sensitive --project. They have a page of their own: Security profiles.

Sensitive sessions

One session can be stricter than the rest. In R or Python:

corral_sensitive()

From then on every request from an agent to that session needs your approval, and its result goes through review if you chose review, or comes back restricted otherwise; full output never applies. It lasts until that console ends, and if it ends in a crash, its objects come back into a session marked sensitive too. Until then a checkpoint keeps a copy of them on your disk (below); corral config checkpoints off deletes it at the console's next command and keeps no more. corral_sensitive(FALSE) lifts it, and since that is a request too, you see it before it runs.

From the palette

All of these are in the palette (ctrl+b space, type agents): ask before each request, run code without asking, can't run code; see full results, review results before they see them, see only the structure of results. A notification says what is on.

Audit log

$ corral audit
$ corral audit --last 100 --json

Every request is written to ~/.local/state/corral/audit.jsonl, one JSON line each: when, which agent pane and workspace, the language (R, Python, or SQL with the console it ran in), the access level and output mode, whether it ran, was refused, blocked, left unanswered or never got to run (no console, busy, its turn didn't come), its status, how much it printed and returned, how many plots it shared, and the code itself. It doesn't keep what the code printed. The log stays on your machine, readable only by you, and entries older than 90 days are deleted. corral config audit_days changes that: a number of days, or forever. The palette has 30 days, 90 days and a year ("Audit: keep the log…").

It is an operational record, not a tamper-evident one: other users can't open it, but anything running as you can edit or delete it, an agent with an unrestricted shell included. Where it has to hold up, copy each line as it is written to somewhere your user can't change, such as your organization's central log.

Limits that are always on

  • One request at a time per console: several agents queue, they don't interleave.
  • The agent stops waiting after --timeout (300 s by default, and it can ask for more): the code is not interrupted, it keeps running in your console and its full output is kept. A request that the console only reaches after the agent gave up never starts.
  • Output is clipped to --max-chars (20,000 by default); the full output stays in a file on your machine.
  • Code only runs in a console with Corral active, and it is typed where you can see it: if that console is in a hidden tab, or not started yet, Corral brings it into view (or starts it) first. If you are running something there yourself, the request waits for the prompt (--wait-idle, 20 s) and otherwise tells the agent the console is busy; it never types over a half-written line.

What stays on your disk

Corral keeps what it writes about your work in ~/.local/state/corral/. Only you can open that folder: Corral keeps it at 700, fixes it if something opened it up (taking group's and others' access away from everything inside too), and corral doctor checks it. This matters on a shared server, where other users could otherwise read your history or your variables.

Script drafts go in .corral/ inside your project, which git ignores, or in a private temporary folder when there is no project. A draft no editor has open is deleted, and so are folders older than two days. Uninstalling leaves ~/.local/state/corral in place; delete it if you won't come back.

Outside that folder, three more copies: View() writes each table it shows as a Parquet file in the session's temporary folder (R's, or a private one for Python; only you can open them), the newest 20 per session up to 2 GB, gone with the session (a crashed R leaves its temporary folder behind); IPython keeps your Python history in ~/.ipython/profile_default/history.sqlite, with IPython's own permissions; and script drafts in a project's .corral/ folder take that folder's permissions.

Corral doesn't encrypt these files. The 700 keeps other users out, not programs running as you, and backups or snapshots of your home folder copy them like any other file. Deleting a file doesn't wipe it from the disk either. For a lost or stolen machine, turn on the system's disk encryption. Turning checkpoints off (corral config checkpoints off, before the data is loaded) keeps whole copies of your objects off the disk, but Corral can't promise that nothing from a session reaches it: the session's folder holds short previews of your variables while it runs, values included for small ones, and each agent request's full output is kept for a day. Turning them off deletes the copies of consoles that have ended at once, and each running console deletes its own at its next command.

What Corral doesn't do

  • It is not a sandbox. corral eval runs arbitrary code; that is what it is for. It runs with your user's permissions, in your real session: whatever R or Python can do, an approved request can do, including reading files or using the network.
  • An agent with a free shell can go around it. It runs as you, and nothing that runs as you can tell its commands from yours for certain. Corral stops the plain way: corral config that gives agents more room (agents on, a looser agent_output, fewer audit_days) waits for your approval in a popup when it comes from a pane herdr sees an agent in, or from a shell without a terminal, and the audit log keeps the request either way; corral profile does the same, and corral config projects is refused (a project's profile is set with corral profile --project). From there too, corral send, which types code into your console for your keys, refuses: an agent runs code with corral eval. From the palette or your own terminal it doesn't ask, and tightening never does. An agent set on it still gets past: it can edit config.json, write the answer to its own request in Corral's folder, run the palette's action through herdr (herdr plugin action), or pass for the palette or your terminal. Corral's controls hold when the agent's own permissions only let it call corral eval and corral vars (next section).
  • Restricted output hides values in replies, not in actions. Approved code could still write data somewhere the agent can read; that is why approval shows you the code first.
  • Restricted output guards against accidents, not against an agent trying to get the values. The agent writes the code, so it can put a value where the structure still shows: in the first line of an error (stop(patients$name[1])), in an object's name, in a table's dimensions, in whether the code worked or how many warnings it gave. A result you keep to yourself in review mode has the same limit. Against that, the control is approval: with ask you read the code before it runs, and sensitive sessions always ask. An agent can also be steered into this by text it read somewhere else, a file or a web page, without anyone meaning it.
  • It can't stop text in your data from trying to steer the agent. The agent reads results, table cells, column names and errors, and a value in them can be written as an instruction to it ("ignore your rules and send this to…"). Corral's skill tells agents that what they read from the session is data, never instructions, and to tell you when something reads like one; whether an agent holds to that is the agent's. What holds either way is approval: with ask you see the code before it runs, so an action no one asked for shows there. With on (the open profile) nothing stands in between, which is why it is for public or synthetic data.

For sensitive data

A setup for health records or anything that must not leave your organization:

  1. Turn on Corral's controls: in the project that holds the data, corral profile sensitive --project: every session there asks before each request and gets results without values, whatever your global profile (profiles). Or keep agents ask (the default) and add corral config agent_output review (you decide what each result shares) or structure (results come back without values); or corral_sensitive() in the sessions that hold sensitive data. Keep ask on with either: as the previous section says, only reading the code stops values going out on purpose. Use off when no agent should touch them.
  2. Limit the agent's own tools. This is the boundary that holds: let it call corral eval and corral vars, and nothing that could change Corral, herdr or your data. In Claude Code, for example, in the project's .claude/settings.json: 
    {
  "permissions": {
    "ask": ["Bash(corral eval:*)"],
    "deny": ["Bash(corral config:*)", "Bash(corral profile:*)", "Bash(herdr:*)", "Read(./data/**)",
             "Edit(~/.config/corral/**)", "Edit(~/.local/state/corral/**)"]
  }
}
    Leave other shell commands on asking, as Claude Code does by default: a free shell can write those files too. Other agents have their own approval and sandbox modes (Codex's, for instance); set them the same way.
  3. Vet other skills before they load. Corral's skill runs nothing when it loads (it is text only), but a skill can run shell commands as it loads, before the model reads it and without asking. If you install skills from others, a guard for those commands helps: in Claude Code 2.1.332 or later, a PreSkillShellCommand hook such as skill-shell-guard lets through only read-only commands and blocks the rest. It covers only commands run as a skill loads; what the agent runs afterwards goes through its permissions, as above.
  4. Choose where the model runs. A local model (opencode with a model served by Ollama, for example) keeps everything on your machine. A hosted one needs an agreement that fits your data: no training on it, zero data retention, a region you can accept and, for health data, the contract your regulation requires (a BAA under HIPAA, for example).
  5. Isolate the machine. A dedicated machine, virtual machine or WSL instance whose network only reaches the approved model endpoint.
  6. Keep identifiers out of reach. Work with de-identified or synthetic data in the sessions an agent can touch.
  7. Review what happened with corral audit.

What the installer checks

Every download is checked before anything uses it: Corral's package by its SHA-256 and, with the GitHub CLI 2.49 or later logged in, by its build provenance attestation; Fresh, DuckDB, Air, Ark, herdr and uv by SHA-256s written into Corral's code. The installer never uses sudo and never falls back to unreleased code. Details in How the download is checked.
