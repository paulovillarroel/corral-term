Security model

Corral runs everything on your machine. Working with an agent, though, means its model sees whatever the agent reads, and that model may be hosted by a provider outside your organization. This page says what goes where, what Corral enforces whatever the agent was told, what it doesn't, and how to set it up for sensitive data such as health records.

Running locally is not the same as staying inside your organization. Corral executes code on your machine, but the agent's model may be hosted elsewhere, and what the agent reads (results, plots, errors) is sent to it under that provider's terms.

Where your data goes

WhatWho can see it
Your files, your data and the objects in your sessionsOnly your machine, until something prints or reads them.
What corral eval prints: results, errors and warnings (up to 20,000 characters by default)The agent, and so its model provider. With restricted output, only whether it worked, the error's first line and the shape of the objects.
New plots from an agent's request, saved as PNG for itThe agent's provider, when the agent opens them. With restricted output they aren't shared.
corral vars --json: names, classes, dimensions and short previewsThe agent's provider. With restricted output, previews of values are removed.
The script draft, when the agent reads it with corral script --readThe agent's provider.
Files the agent opens with its own toolsGoverned by the agent's own permissions, not by Corral (see below).
Corral itselfSends nothing, except one anonymous ping when an installation finishes (install count).

What Corral enforces

These controls live in Corral's code, not in the agent's instructions: they apply whatever the model decides.

Access levels

$ corral config agents ask
$ corral config agents off
$ corral config agents on
  • on (the default): an agent's corral eval runs in your console, where you watch it.
  • ask: every request opens a popup with the exact code, which agent pane asked and what it will see back. Enter runs it; n or Esc refuses, and the agent is told not to try again unless you ask. With no answer in 5 minutes, nothing runs.
  • off: corral eval refuses everything.

Restricted output

$ corral config agent_output structure

The code still runs on your real data and you see its output in your console, but the agent only gets back whether it worked, the first line of an error, how many warnings there were, and the shape of the session's objects: names, classes, the dimensions of tables, the signatures of functions. No printed values, no previews, no plots. For example:

[corral] restricted output: the agent doesn't see values (5 lines printed in the user's console)
[corral] 1 warning(s), not shown
[corral] objects: pacientes (data.frame, 3 × 3); resumen (summaryDefault)
[corral] 1 new plot(s) for the user (ctrl+b f); not shared with the agent (restricted output)

full (the default) returns everything.

Sensitive sessions

One session can be stricter than the rest. In R or Python:

corral_sensitive()

From then on every request from an agent to that session needs your approval and gets restricted output, whatever the settings above say. It lasts until that console ends; corral_sensitive(FALSE) lifts it, and since that is a request too, you see it before it runs.

Audit log

$ corral audit
$ corral audit --last 100 --json

Every request is written to ~/.local/state/corral/audit.jsonl, one JSON line each: when, which agent pane and workspace, R or Python, the access level and output mode, whether it ran, was refused, blocked or left unanswered, its status, how much it printed and returned, how many plots it shared, and the code itself. The log stays on your machine.

Limits that are always on

  • One request at a time per console: several agents queue, they don't interleave.
  • A request that isn't done in time is cut (--timeout, 300 s by default), and one that the console only reaches after the agent gave up never runs.
  • Output is clipped to --max-chars (20,000 by default); the full output stays in a file on your machine.
  • Code only runs in a console that has Corral active and is in view; it is typed where you can see it.

What Corral doesn't do

  • It is not a sandbox. corral eval runs with your user's permissions, in your real session: whatever R or Python can do, an approved request can do, including reading files or using the network.
  • An agent with a free shell can go around it. It runs as you, so it could change Corral's settings, write files or use other tools. Corral's controls hold when the agent's own permissions only let it call corral eval and corral vars (next section).
  • Restricted output hides values in replies, not in actions. Approved code could still write data somewhere the agent can read; that is why approval shows you the code first.
  • Error messages can carry values. With restricted output only their first line is returned, but it is returned.

For sensitive data

A setup for health records or anything that must not leave your organization:

  1. Turn on Corral's controls: corral config agents ask and corral config agent_output structure, or corral_sensitive() in the sessions that hold sensitive data. Use off when no agent should touch them.
  2. Limit the agent's own tools. Let it call corral eval and corral vars, and nothing that could change Corral, herdr or your data. In Claude Code, for example, in the project's .claude/settings.json: 
    {
  "permissions": {
    "ask": ["Bash(corral eval:*)"],
    "deny": ["Bash(corral config:*)", "Bash(herdr:*)", "Read(./data/**)", "Edit(~/.config/corral/**)"]
  }
}
    Other agents have their own approval and sandbox modes (Codex's, for instance); set them the same way.
  3. Choose where the model runs. A local model (opencode with a model served by Ollama, for example) keeps everything on your machine. A hosted one needs an agreement that fits your data: no training on it, zero data retention, a region you can accept and, for health data, the contract your regulation requires (a BAA under HIPAA, for example).
  4. Isolate the machine. A dedicated machine, virtual machine or WSL instance whose network only reaches the approved model endpoint.
  5. Keep identifiers out of reach. Work with de-identified or synthetic data in the sessions an agent can touch.
  6. Review what happened with corral audit.
