Security model

Corral runs everything on your machine. Working with an agent, though, means its model sees whatever the agent reads, and that model may be hosted by a provider outside your organization. This page says what goes where, what Corral enforces whatever the agent was told, what it doesn't, and how to set it up for sensitive data such as health records.

Running locally is not the same as staying inside your organization. Corral executes code on your machine, but the agent's model may be hosted elsewhere, and what the agent reads (results, plots, errors) is sent to it under that provider's terms.

Where your data goes

What Corral enforces

These controls live in Corral's code, not in the agent's instructions: they apply whatever the model decides.

Access levels

$ corral config agents ask
$ corral config agents on
$ corral config agents off
  • ask (the default): every request opens a popup with the exact code, which agent asked (Claude Code, Codex… and its pane, or "outside herdr" when no pane did) and what it will see back. What you read is what runs: control and invisible characters, which a terminal would act on or draw as nothing, show as ␛, ␍ or <U+202E> under a warning, and long lines wrap instead of being cut. The console prints such code written out too, before its echo. Enter runs it; n or Esc refuses, and the agent is told not to try again unless you ask. With no answer in 5 minutes, nothing runs. A missing or mistyped setting also asks. The popup ignores keys for its first 0.6 seconds, so a key you meant for another pane, an Enter sending a message to your agent for instance, can't answer it.
  • on: an agent's corral eval runs in your console, where you watch it, without asking first. Whatever can call corral eval as you, an agent or a script, can run any code in your session. Watching is not the same as reading, so choose it only when the speed is worth more than reading every request.
  • off: corral eval refuses everything.

Restricted output

$ corral config agent_output structure

The code still runs on your real data and you see its output in your console, but the agent only gets back whether it worked, the first line of an error, how many warnings there were, and the shape of the session's objects: names, classes, the dimensions of tables, the signatures of functions. No printed values, no previews, no plots. For example:

[corral] restricted output: the agent doesn't see values (5 lines printed in the user's console)
[corral] 1 warning(s), not shown
[corral] objects: patients (data.frame, 3 × 3); overview (summaryDefault)
[corral] 1 new plot(s) for the user (ctrl+b f); not shared with the agent (restricted output)

full (the default) returns everything.

Review mode

$ corral config agent_output review

The middle ground, for when the agent should help you draw conclusions but you want to see what it reads first. The code runs; then a popup shows you the result exactly as the agent would get it, with any new plots, without its colors and with any other character that could hide text written out. Enter shares it. n keeps it to you, and the agent gets only the structure, plus a note to ask you what you found. You might share a table of counts and keep a listing of patients, for example.

Code that prints nothing, like an assignment, doesn't ask. With no answer in 5 minutes, the result is kept. corral vars --json leaves out previews of values in this mode, since they would skip your review.

Sensitive sessions

One session can be stricter than the rest. In R or Python:

corral_sensitive()

From then on every request from an agent to that session needs your approval, and its result goes through review if you chose review, or comes back restricted otherwise; full output never applies. It lasts until that console ends, and if it ends in a crash, its objects come back into a session marked sensitive too. Until then a checkpoint keeps a copy of them on your disk (below); turn checkpoints off with corral config checkpoints off if that copy mustn't exist. corral_sensitive(FALSE) lifts it, and since that is a request too, you see it before it runs.

From the palette

All of these are in the palette (ctrl+b space, type agents): ask before each request, run code without asking, can't run code; see full results, review results before they see them, see only the structure of results. A notification says what is on.

Audit log

$ corral audit
$ corral audit --last 100 --json

Every request is written to ~/.local/state/corral/audit.jsonl, one JSON line each: when, which agent pane and workspace, the language (R, Python, or SQL with the console it ran in), the access level and output mode, whether it ran, was refused, blocked, left unanswered or never got to run (no console, busy, its turn didn't come), its status, how much it printed and returned, how many plots it shared, and the code itself. It doesn't keep what the code printed. The log stays on your machine, readable only by you, and entries older than 90 days are deleted. corral config audit_days changes that: a number of days, or forever. The palette has 30 days, 90 days and a year ("Agents: keep the audit log…").

Limits that are always on

  • One request at a time per console: several agents queue, they don't interleave.
  • The agent stops waiting after --timeout (300 s by default, and it can ask for more): the code is not interrupted, it keeps running in your console and its full output is kept. A request that the console only reaches after the agent gave up never starts.
  • Output is clipped to --max-chars (20,000 by default); the full output stays in a file on your machine.
  • Code only runs in a console with Corral active, and it is typed where you can see it: if that console is in a hidden tab, or not started yet, Corral brings it into view (or starts it) first. If you are running something there yourself, the request waits for the prompt (--wait-idle, 20 s) and otherwise tells the agent the console is busy; it never types over a half-written line.

What stays on your disk

Corral keeps what it writes about your work in ~/.local/state/corral/. Only you can open that folder: Corral keeps it at 700, fixes it if something opened it up (taking group's and others' access away from everything inside too), and corral doctor checks it. This matters on a shared server, where other users could otherwise read your history or your variables.

Script drafts go in .corral/ inside your project, which git ignores, or in a private temporary folder when there is no project. A draft no editor has open is deleted, and so are folders older than two days. Uninstalling leaves ~/.local/state/corral in place; delete it if you won't come back.

What Corral doesn't do

  • It is not a sandbox. corral eval runs arbitrary code; that is what it is for. It runs with your user's permissions, in your real session: whatever R or Python can do, an approved request can do, including reading files or using the network.
  • An agent with a free shell can go around it. It runs as you, and nothing that runs as you can tell its commands from yours for certain. Corral stops the plain way: corral config that gives agents more room (agents on, a looser agent_output, fewer audit_days) waits for your approval in a popup when it comes from a pane herdr sees an agent in, or from a shell without a terminal, and the audit log keeps the request either way. From the palette or your own terminal it doesn't ask, and tightening never does. An agent set on it still gets past: it can edit config.json, write the answer to its own request in Corral's folder, run the palette's action through herdr (herdr plugin action), or pass for the palette or your terminal. Corral's controls hold when the agent's own permissions only let it call corral eval and corral vars (next section).
  • Restricted output hides values in replies, not in actions. Approved code could still write data somewhere the agent can read; that is why approval shows you the code first.
  • Restricted output guards against accidents, not against an agent trying to get the values. The agent writes the code, so it can put a value where the structure still shows: in the first line of an error (stop(patients$name[1])), in an object's name, in a table's dimensions, in whether the code worked or how many warnings it gave. A result you keep to yourself in review mode has the same limit. Against that, the control is approval: with ask you read the code before it runs, and sensitive sessions always ask. An agent can also be steered into this by text it read somewhere else, a file or a web page, without anyone meaning it.

For sensitive data

A setup for health records or anything that must not leave your organization:

  1. Turn on Corral's controls: keep agents ask (the default), and add corral config agent_output review (you decide what each result shares) or structure (results come back without values); or corral_sensitive() in the sessions that hold sensitive data. Keep ask on with either: as the previous section says, only reading the code stops values going out on purpose. Use off when no agent should touch them.
  2. Limit the agent's own tools. This is the boundary that holds: let it call corral eval and corral vars, and nothing that could change Corral, herdr or your data. In Claude Code, for example, in the project's .claude/settings.json: 
    {
  "permissions": {
    "ask": ["Bash(corral eval:*)"],
    "deny": ["Bash(corral config:*)", "Bash(herdr:*)", "Read(./data/**)",
             "Edit(~/.config/corral/**)", "Edit(~/.local/state/corral/**)"]
  }
}
    Leave other shell commands on asking, as Claude Code does by default: a free shell can write those files too. Other agents have their own approval and sandbox modes (Codex's, for instance); set them the same way.
  3. Choose where the model runs. A local model (opencode with a model served by Ollama, for example) keeps everything on your machine. A hosted one needs an agreement that fits your data: no training on it, zero data retention, a region you can accept and, for health data, the contract your regulation requires (a BAA under HIPAA, for example).
  4. Isolate the machine. A dedicated machine, virtual machine or WSL instance whose network only reaches the approved model endpoint.
  5. Keep identifiers out of reach. Work with de-identified or synthetic data in the sessions an agent can touch.
  6. Review what happened with corral audit.

What the installer checks

Every download is checked before anything uses it: Corral's package by its SHA-256 and, if you have the GitHub CLI, by its build provenance attestation; Fresh, DuckDB, Air and Ark by SHA-256s written into Corral's code. The installer never uses sudo and never falls back to unreleased code. Details in How the download is checked.
