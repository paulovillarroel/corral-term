Threat model

What Corral protects, from whom, how, and what it leaves to the agent's own permissions, to the machine and to your organization. The Security model explains each control; this page sets them against the threats.

What it protects

  • Your data. The objects in your R and Python sessions, and the copies Corral keeps of them on disk: previews, plots, checkpoints, full outputs.
  • Your code. Scripts, drafts and the history of what you typed.
  • The rules. The access level, the output mode, profiles and sensitive sessions, and the audit log that records how they were used.

Who it guards against

WhoWhat they can do
Your agent, doing its jobWrites code and reads results; it can misread what you asked or make a mistake.
Your agent, steered by what it readA file, a web page or a package's documentation with instructions in it (prompt injection) can lead it to go after values or the rules, without anyone meaning it.
Another user on the same machineOn a shared server: lists processes, connects to ports on 127.0.0.1, reads any file open to them.
A web page in your browserSends requests to 127.0.0.1 from your browser; it can't read the answers unless the server lets it.
Another program running as youAnything your user can do: read Corral's files and keys, change its settings, type into panes. An agent with an unrestricted shell is one.
Whoever tampers with a downloadChanges Corral's package or one of its tools on the way to your machine.

Between Corral's parts

Corral's processes talk to each other on your machine. Each channel is closed to other users and to web pages, but for a window of a few milliseconds when the editor's language server starts (below); a program running as you can use all of them, as it can everything else.

ChannelWhat goes through itHow it is closed
An agent's request to the consoleThe code, in a file in the session's folder; herdr then types a call to it in the consoleCorral's folder (700) and herdr's socket, which only you can open (0600)
The R console and ArkCode, output and results, as Jupyter messages over ZeroMQUnix sockets in Corral's folder; when that folder's path is too long for a socket address, in a new folder of their own with a short path, made 700, under $XDG_RUNTIME_DIR (usually /run/user/UID), $TMPDIR or /tmp, where every folder above it is yours or root's and closed to others' writes (or sticky). The same with the Jupyter console frontend (ark_frontend jupyter). Each message is signed with HMAC-SHA256, with a 128-bit key from the system's random source, new each time R starts, kept in a file only you can read (with the Jupyter console frontend, jupyter_client makes the key). Never TCP, where another user could read its output (the key signs messages, it doesn't hide them): if no private folder can be made, the console doesn't start and says why.

Supply chain

  • Corral itself. One Rust binary with no dependencies beyond Rust's standard library: Cargo.lock lists only Corral.
  • Each release. Built by GitHub Actions with --locked, in a workflow whose actions are pinned to a commit, since a tag can be moved. The package gets a SHA-256 and a build provenance attestation.
  • The installer. Checks every download before using it: Corral's package by its SHA-256 and, with the GitHub CLI installed and logged in, its attestation (the SHA-256 comes from the same release, so the attestation is what catches a release replaced at its source); Fresh, DuckDB, Air, Ark, herdr and uv by SHA-256s written into Corral's code. It never uses sudo (how the download is checked).
  • What it can't vouch for. The packages the consoles use come from their repositories, under those repositories' own checks: for Python, IPython, cloudpickle, pyarrow and duckdb from PyPI through uv (the version your project pins wins); for R, jsonlite, httpgd and the rest from CRAN or Posit's package manager; and any package you install. Also skills from others (vet them before they load) and the agent itself.
